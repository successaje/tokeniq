# Data model

Source of truth: [`packages/db/src/schema.ts`](../packages/db/src/schema.ts) (Drizzle) and the SQL migrations in [`packages/db/migrations`](../packages/db/migrations).

## Conventions

- **Ids:** text UUIDs generated by the application. Better Auth tables use text ids too.
- **Times:** timestamps are `timestamptz`; calendar due dates are `date`, and obligation maths happens in UTC calendar days.
- **Money:** USD values are `numeric(38,18)` and raw token amounts are `numeric(78,0)`. The Postgres driver returns both as strings (`pg.types.setTypeParser`), so no value passes through a JavaScript float.
- **Organization scope:** every organization-owned row carries `organization_id`, and every query filters by it. Organization scope is also checked by membership middleware.
- **Append-only:** `audit_events`, `approvals` and `policy_versions` reject `UPDATE` and `DELETE`, and `safe_signatures` rejects `UPDATE`. A trigger (`tokeniq_reject_mutation`, migration `0001`) enforces this, so the rule holds even for code with direct SQL access.

## Entities

| Table | Purpose | Key constraints |
|---|---|---|
| `users`, `sessions`, `accounts`, `verifications` | Better Auth identity, sessions and one-time code verification records | `users.email` unique (case-insensitive); `sessions.token` unique |
| `passkeys` | WebAuthn credentials | `credential_id` unique |
| `wallet_addresses` | Wallets used for Sign-In with Ethereum (login only; not treasury verification) | unique per address and chain |
| `organizations`, `members`, `invitations` | Organizations, role memberships (owner/admin/finance/approver/viewer), email invitations | one membership per user per organization |
| `org_profiles` | Purpose, reporting currency, `is_sample` flag, onboarding progress | primary key `organization_id` |
| `policy_versions` | Versioned treasury and approval policies, each with a reason and author | unique `(organization_id, kind, version)`; append-only |
| `treasury_accounts` | Tracked Safes and wallets: kind, purpose, include flag, verification (method, signer, time), Safe metadata (owners, threshold, version, nonce, guard, modules), sync status | unique `(organization_id, chain_id, address)`; archived accounts are kept |
| `address_challenges` | Single-use signed challenges that prove control of an address | unique `nonce`; expiry and `used_at` |
| `balance_snapshots` | Raw balance of one asset in one account at one block, with block hash and time | unique `(account_id, asset_address, block_number)`, which makes syncs idempotent |
| `position_snapshots` | Shares, underlying assets and withdrawable amount of a venue position at one block | unique `(account_id, venue_id, block_number)` |
| `price_observations` | Chainlink rounds: answer, decimals, round id, the feed's own `updated_at` | unique `(chain_id, feed, round_id)` |
| `obligations` | Commitments and expected inflows: amount and currency, first due date, recurrence (JSON), certainty (estimate/committed/invoiced), priority, status, `track_from`, counterparty, recipient, invoice number, notes | — |
| `obligation_documents` | Uploaded supporting files (bytea, ≤ 5 MB), type, size, SHA-256 | — |
| `payments` | Settlement of one occurrence: `paid_verified` (matched on-chain transfer), `paid_unverified` (recorded by a member) or `skipped`, plus tx hash, decoded match and verification details | unique `(obligation_id, due_date)` |
| `opportunities`, `opportunity_snapshots` | Latest venue data (JSON in the engine's `Opportunity` shape) and APY/TVL/liquidity history | `listed` is recomputed from code on every refresh |
| `recommendations` | Engine recommendations with full reasoning; status open/accepted/dismissed/superseded | unique `(organization_id, fingerprint)` |
| `proposals` | Structured actions moving through approval, signatures and execution: validation at creation, prepared Safe transaction, `safe_tx_hash`, simulation, expiry | unique `(organization_id, idempotency_key)`; unique `safe_tx_hash` |
| `approvals` | Internal approve/reject decisions with role and comment | append-only |
| `proposal_comments` | Discussion | — |
| `safe_signatures` | Owner signatures over a `safe_tx_hash` | unique `(safe_tx_hash, signer)`; no updates |
| `executions` | Submitted transactions: receipt status, the Safe's own success event, block, gas, reconciliation time | unique `(chain_id, tx_hash)` |
| `risk_alerts` | Alert lifecycle (open/acknowledged/resolved) keyed by condition fingerprint | partial unique `(organization_id, fingerprint)` while not resolved |
| `notifications` | In-app notifications per user | unique `(user_id, dedupe_key)` |
| `audit_events` | Every state change: actor (user/system/copilot), action, target, data, IP, user agent | append-only; `bigserial` id used as the activity cursor |
| `provider_health` | Measured status of RPCs, Chainlink, sequencer feeds, the Morpho API and Aave reads | primary key `provider` |
| `idempotency_keys` | Reserved for replaying responses to financial writes | unique `(organization_id, user_id, key)` |
| `copilot_threads`, `copilot_messages` | Private copilot conversations, stored exactly as exchanged (append-only replay), with token usage | — |

## Derived values (never stored as truth)

These are computed by `@tokeniq/core` from the stored observations each time they are read, so they always use the current policy and data:
- treasury totals;
- reserve requirement, coverage and deployable surplus;
- the projection;
- policy checks.

Recommendations and alerts are stored only so their lifecycle (dismissed, acknowledged, resolved) can be tracked. They are recomputed on read and on every sync.

## Migrations and recovery

- **Creating a migration:** `pnpm db:generate` creates SQL from schema changes; write custom SQL with `drizzle-kit generate --custom`.
- **Applying migrations:** `pnpm db:migrate`. Production runs this as a release step before traffic switches (`preDeployCommand`).
- **No down migrations.** Every migration must be backward-compatible with the running release (expand then contract). Recovery from a bad migration is restore-from-backup plus redeploying the previous release; see [`OPERATIONS.md`](OPERATIONS.md).
