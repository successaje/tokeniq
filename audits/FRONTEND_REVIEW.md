# Frontend review (apps/web)

> **Internal self-review.** This is a review of TokenIQ's own web app by an AI-assisted engineering process working inside the team. It is **not an audit** and **not an independent third-party review**. Treat its conclusions as a starting point for an external review, not a substitute for one.

- **Date:** 2026-10-11
- **Scope:** `apps/web` only (Next.js 16 App Router, React 19, Tailwind v4, Radix, wagmi 3 / viem, TanStack Query). The API (`apps/api`) and packages were read for context but not changed; API-side issues are listed as **Open** with the change needed.
- **Tree:** git worktree `tokeniq-2`, branch `tokeniq-2`, uncommitted `apps/web` changes on top of `3641224a` (started on `4df32c4`; the API commits in between are covered in FR-14 and FR-39 to FR-45). Line numbers below refer to the tree **after** the fixes in this review.

## Method

1. Read the intended design first: `docs/contributing/frontend-conventions.md`, `docs/ARCHITECTURE.md`, ADRs 0001, 0003, 0005, 0006 and 0007.
2. Line-by-line reading of the code on the money and signing paths: `components/app/approvals/*`, `app/app/approvals/[id]`, `components/wallet/*`, `lib/{api,org,auth-client,wagmi,format}.ts`, `components/ui/{field,money,identity,dialog,toast,button}.tsx`, `components/auth/*`, `components/pwa/*`, `public/sw.js`, `next.config.ts` and `components/app/copilot/markdown.tsx`. The API handlers they call (`apps/api/src/modules/proposals.ts`, `packages/chain/src/{safe,multisend,erc4626,aave,safe-deployments}.ts`) were read to check the contract between them.
3. Targeted searches across `apps/web/src` for `dangerouslySetInnerHTML`, `target="_blank"`, `window.open`, `href={…}` built from data, `aria-label` on role-less elements, `parseFloat`/`Number(` on money, `localStorage`, query keys outside `["org", orgId, …]`, `NEXT_PUBLIC_*`.
4. Exercised the running app in the built-in browser (dev server, sample workspace): sign-in, onboarding, sample banner, recommendation → proposal, proposal page, page titles, overview at 412 px. No real wallet was connected and nothing was signed.
5. Proved behaviour with code where possible: Node checks of URL parsing for the redirect bug and of the Next router's external-URL handling, and new unit tests (`vitest`) for the Safe-transaction verifier and the input guards.
6. Folded in findings from the Playwright + axe-core suite (`apps/e2e`, WCAG 2.0–2.2 A/AA, production build), three items from the PRD cross-check, the known deviations in `docs/DESIGN_SYSTEM.md` §13 (items 1, 3 and 9), and the client changes required by API commits `3e57c556` (payee hold, policy snapshots) and `3641224a` (permissions, sync rate limit, invitation email status, sample workspaces, idempotency), all reported by the lead on 2026-10-11.
7. Because the suite stops at the first failing page, also ran axe-core with the same tags over all 19 app views (including the settings tabs), a proposal page and an obligation page, in light and dark, against the dev server with a fresh sample workspace. That covered pages the suite doesn't reach (FR-46).

## Details (Medium and above)

### FR-01 (High): the signed typed data was not checked against what the owner was shown

**Before.** `SignInner` passed `p.safeTx.typedData` to `signTypedData` after converting number fields. The review box rendered other fields of the same response: `safeTx.nonce`, `safeTxHash` truncated to 8+8 hex characters (`title` tooltip only), the `calls[].description` strings and `shortAddress(c.to)`. Nothing tied the two together, and the network, `operation` (CALL vs DELEGATECALL), value and refund fields were never shown. The API recovers each signature against the stored safeTxHash, so a mismatched signature could not be *recorded*. But the owner would still have produced a valid signature over something they never reviewed. A signature is a bearer credential: anyone holding enough of them can submit them to the Safe directly. Unless the owner's wallet decoded the transaction itself, a DELEGATECALL to an arbitrary contract (the pattern behind recent large Safe thefts) would have looked like any other request.

**Fix.** `components/app/approvals/safe-tx.ts` independently verifies the prepared transaction before any wallet is asked to sign, using the token list from `/api/v1/meta`:

1. Typed-data shape: `primaryType` is `SafeTx`, the `SafeTx` type matches Safe.sol v1.3.0–v1.5.0 field for field, and the domain is exactly `{chainId, verifyingContract}`.
2. The domain chain equals the proposal's chain (and the source account's). `verifyingContract` equals the Safe shown and the account being spent from.
3. The message fields parse strictly and equal the stored `to`, `value`, `data`, `operation` and `nonce` shown.
4. `safeTxGas`, `baseGas`, `gasPrice`, `gasToken` and `refundReceiver` are all zero. Non-zero values would let whoever submits take a refund from the Safe.
5. A DELEGATECALL must target canonical MultiSendCallOnly (v1.3.0 canonical and eip155, v1.4.1, v1.5.0, mirrored from `packages/chain`; drift fails closed). The packed batch is decoded, every inner operation must be CALL, and the inner calls must equal the calls displayed.
6. Each call is decoded against the functions TokenIQ's builders produce. It must be one this proposal kind can contain, must not send ETH, and must touch only tokens on the supported list (matching the action's symbol). Its arguments must match the action: approve the spender called next, for exactly the amount or zero; transfer exactly the amount to the proposal's recipient; deposit, supply and withdraw exactly the amount, with receiver, owner and `onBehalfOf` all equal to the Safe.
7. `hashTypedData` of the exact request object equals the displayed `safeTxHash`.

Any failure renders a danger callout listing every reason, and no Sign or Submit button appears. The wallet receives the verified request object itself, so what is hashed and what is signed cannot diverge. After signing, the signer is recovered locally and must equal the connected account before anything is posted. The new `SafeTxReviewPanel` shows network and chain ID, the Safe, Safe version, nonce, operation, `to`, ETH value, refund fields, the full **safeTxHash, domain hash and message hash**, and each decoded call with full contract and argument addresses and exact token amounts plus raw base units. Hashes and addresses are shown in full as wrapping, selectable monospace text in 4-character groups with a copy button, never only in a tooltip; the lead's item A is covered here. Owner and connected-wallet addresses on the signing path are shown in full too. Unit tests: `safe-tx.test.ts` (15 cases, including a hash mismatch, nonce mismatch, DELEGATECALL to a non-canonical target, refund fields, displayed-vs-signed call mismatch, wrong receiver, wrong recipient or amount, wrong chain or Safe, unknown token and undecodable function).

### FR-02 (Medium): a broadcast transaction could be lost and submitted again

**Before.** In `ExecuteInner`, if `sendTransactionAsync` returned a hash and `POST /executions` then failed (network, 5xx, rate limit), the error was shown, the phase returned to `idle` and the "Submit transaction" button reappeared. The proposal stayed `ready_to_execute`, so clicking again fetched fresh calldata and broadcast a second transaction. One of the two would revert on the Safe nonce, spending gas. The first was never tracked, so the proposal never reached `submitted` or `executed` and would later go `stale`. A reload lost the hash entirely.

**Fix.** The hash is saved in `localStorage` (per proposal and safeTxHash) right after the wallet returns it. While it is unrecorded, the panel shows "Transaction sent: do not submit it again", with the full hash and an explorer link, and offers only **Record this transaction**. The API accepts re-recording from `ready_to_execute`, `submitted` or `failed`. A ref guard prevents re-entry. The never-replaced "pending" toast is now replaced by the actual outcome ("Submitted, not executed yet" or "Sent, but not recorded"), and the page states that submitted is not executed.

### FR-03 (Medium): execTransaction calldata was not checked

**Fix.** `verifyExecutionData` decodes the API's `execTransaction` calldata. It requires the reviewed chain, the reviewed Safe as `to`, a value of 0, inner `to`/`value`/`data`/`operation` and refund fields identical to the reviewed SafeTx, and at least `threshold` × 65 signature bytes. Failures are listed and nothing is sent to the wallet. The transaction is sent to `review.safe` on `review.chainId`, not to the response's own fields.

### FR-04 (Medium): signing and submission were offered when they shouldn't be

**Fix.** The Sign panel renders only while `validationNow.valid`. The Submit panel needs `validationNow.valid` and the `proposals.execute` permission, which is now in the client mirror. That mirror is a typed `as const satisfies Record<string, readonly Role[]>`, so a misspelled permission no longer compiles; before, it would have thrown at runtime. A short line explains why each control is unavailable. The API remains the boundary.

### FR-05 (Medium, Open, API): signatures are accepted after policy stops passing

**API change needed:** in `POST /api/v1/orgs/{orgId}/proposals/{id}/signatures`, run the same `validateAction(actionFromJson(p.action), validationContext(state, action))` as `execution-data` before storing the signature. On failure, respond `422 policy_check_failed` with `validationDto(live)` as details. Optionally do the same in `prepare` (it already re-validates according to ADR 0005; confirm it rejects).

**Related API change (FR-34, Low):** before marking a proposal `stale` on `nonce_moved`, check whether the Safe emitted `ExecutionSuccess(txHash = safeTxHash)` (or `ExecutionFailure`) for this proposal's safeTxHash. If it did, record that transaction as the execution (`submitted`, then let the tracker confirm it) instead of asking owners to re-sign. Also let `/executions` accept a hash for a `stale` proposal when the receipt shows it executed this safeTxHash.

### FR-06 (Medium): open redirect after sign-in

**Before.** `safeNext` accepted any string starting with `/` that didn't start with `//` or `/\`. The WHATWG URL parser removes ASCII tab, LF and CR, so `new URL("/\t/evil.example", origin)` is `http://evil.example/` (checked with Node). Next 16's router treats a different origin as external and does a hard navigation (`navigate-reducer.js` → `completeHardNavigation`). A link like `https://tokeniq.app/login?next=/%09/evil.example` therefore sent people to an attacker's page right after a genuine sign-in, an effective phishing setup ("session expired, sign in again").

**Fix.** `lib/sanitize.ts` `safeNext` rejects control characters and backslashes, resolves the value against the current origin, requires the same origin, and returns only `pathname + search + hash`. Tests in `lib/sanitize.test.ts`.

### FR-07 (Medium, Open, lead decision): `'unsafe-inline'` in `script-src`

Next.js inline bootstrap scripts need either `'unsafe-inline'` or a per-request nonce. **Options:** (a) a nonce-based CSP set in `proxy.ts` (Next 16 middleware) with `'strict-dynamic'`, which makes every page dynamically rendered (the marketing pages included) and requires the theme script to carry the nonce; (b) keep `'unsafe-inline'` only for marketing routes and use a nonce under `/app`, `/login` and `/onboarding`; (c) accept the risk with a documented rationale. Today no `dangerouslySetInnerHTML` takes data (only the static theme script), the copilot renderer never emits HTML, and user text is always rendered as text, so this is defence in depth that is missing, not a known injection.

### FR-08 (Medium): `/app` wider than a phone screen

**Cause.** The overview grid had no explicit column template on small screens, so its single implicit column was `auto`, sized to the widest child's min-content. `ProjectionChart` starts at `width = 640` and renders `<svg width={640}>`. That widened the column to 674 px, and the chart's ResizeObserver then measured the widened wrapper and kept 640.

**Fix.** `grid-cols-1` (`minmax(0, 1fr)`) on both overview grids; the SVG gets `max-w-full` so its measured width can never size its container. Separately, the observer is re-attached once the chart has enough points (`[measurable]`). Before, it ran once on mount and never attached if the first render was the "not enough data" branch. In the browser, `scrollWidth` went from 690 to 412 at a 412 px viewport.

### FR-09 – FR-12 (Medium, e2e axe)

- **FR-09:** `<Money>` now renders the visible figure `aria-hidden` plus an `sr-only` exact amount ("approximately $1,745,450.00, source" when relevant). The landing `BigMoney` does the same. Nav badges use an `sr-only` ", N need attention". The network chip row is `role="group"` and the verification message `<pre>` is `role="region"`.
- **FR-10:** each KPI is a `<div>` group whose only children are `dt` and `dd`. The link moved inside the value `<dd>`, stretched over the group (`after:inset-0`), with an `sr-only` suffix naming the destination and a focus ring on the group (`has-[a:focus-visible]`). The Reserves `Stat` and Balances `Kpi` follow the same pattern. Notes inside definition lists (reserve rule cards, venue sheet hints) are now a second `<dd>` in the same group.
- **FR-11:** the bar is one `role="img"` whose name lists every segment's label, amount and share. Segments are plain divs that still highlight on hover, and the legend carries the same values as text. The hover tooltip is `aria-hidden` (it duplicated the image name).
- **FR-12:** the footer "Support details" link is underlined. The rest of the app's colour-only links were swept under FR-31.

### FR-13 (Medium): page state survived an organization switch

**Fix.** The shell's `<main>` is keyed by `orgId`, so switching remounts the page. No page-local state (a copilot thread, a half-filled sheet, a selected proposal) carries over. The query cache was already keyed by org and is still cleared on switch.

### FR-14 (Medium, fixed in the API by `3e57c556`): live re-validation double-counted the proposal being validated

**Evidence (sample workspace, 2026-10-11).** The recommendation "Deploy $349,000 into Gauntlet USDC Prime" showed deployable $872,725.00 and a post-action deployed share of 20.0%. The proposal created from it showed "Deployable surplus is $523,725.00" ($872,725 − $349,000), "$698,000.00 deployed vs 50% limit" (2 × $349,000) and "deployed share 40.0%". `validationContext` builds on `state.reserve`, whose `pendingOutflows` already include this proposal (`ACTIVE_PROPOSAL_STATUSES` starts at `pending_approval`). The engine then applies the action again.

**Change requested, now made:** when re-validating proposal `X`, build the context from an `OrgState` that excludes `X` from `pendingOutflows` and pending exposure. Commit `3e57c556` added `loadOrgState(db, orgId, now, { excludeProposalId })` and uses it in GET `/proposals/{id}`, the decision handler, `/prepare`, `/signatures` and `/execution-data`. Confirmed by reading the code; the UI figures were not re-measured after the change. A core test pinning "a proposal for exactly the deployable amount passes its own re-validation" is still worth adding if it isn't there.

### FR-36 (Medium): input boundaries below 3:1

Every `Input`, `Textarea`, `AmountInput`, `AddressInput`, `Select` and `GroupedSelect` gets its border from `inputClass` in `components/ui/field.tsx`, which drew `border-border-strong/50`. Against `surface` that is 1.67:1 (light) and 1.72:1 (dark), so on a white card a field's edge is close to invisible to low-vision users (WCAG 1.4.11 needs 3:1 for the visual information required to identify a component). The full-strength token measures 3.14:1 and 3.22:1. It is now used for `inputClass`, the type-to-confirm input, the copilot textarea, the switch track, and the unchecked radio and checkbox indicators (`radio-cards`, `checkbox-chips`, `occurrence-picker`, the invite role picker). Hover moves to `text-3` so a hover cue remains. Secondary buttons keep their lighter border: their label identifies them, so 1.4.11 does not require a visible boundary.

### FR-39 (Medium): saving the approval policy reset the new-payee hold

`3e57c556` added `newPayeeHoldHours` (default 48, 0 disables, max 336) to the approval policy schema. The settings form built its PUT body from tiers, self-approval and TTL only. The API parses with `.default(48)`, so every save from Settings → Approvals, even one that only changed a tier bound, silently set the hold back to 48 hours. An organization that had set a 14-day hold would drop to 2 days, and one that had switched the hold off (0) would get it back, both without anything in the diff the editor saw. **Fix:** the draft now carries `newPayeeHoldHours` (initialised from the server, or 48 for older policies), validates 0–336 like the API, always sends it, and states it in the plain-language preview. The field label is "Hold payments to new or changed payee addresses". The obligation page now shows when the payee address was set and until when payments to it are held (FR-40).

## Checked and fine

**1. Signing safety (beyond FR-01 to FR-05).** Execution is offered only in `ready_to_execute`, never for sample workspaces, and the API enforces the same. A wrong wallet network is handled with an explicit "Switch wallet network" before signing; for submission the switch happens first and wagmi refuses to send on a different chain (`chainId` is passed). The connected account is compared with the Safe owners before Sign is offered, and "already signed" is detected. Internal approval, Safe signature and on-chain execution are labelled as separate gates throughout, and statuses use icon + text. Stale nonces surface as "Needs re-signing" with a re-prepare action. Mutations are never retried automatically (`mutations: { retry: false }`), and buttons disable while pending. The sample-workspace proposal shows the warning callout and no prepare, sign or submit controls.

**2. XSS and injection.** The only `dangerouslySetInnerHTML` is the static theme script in `app/layout.tsx` and `app/global-error.tsx` (a template with a constant key, no user data). The copilot renderer builds React elements only, never HTML, and does not link arbitrary URLs. Org names, obligation titles, comments (`whitespace-pre-wrap` text), recipient labels and notification text are rendered as text. External links use `rel="noreferrer noopener"` (the toast action uses `noreferrer`, which implies `noopener`). Opportunity URLs go through `safeHref`. Explorer URLs are built from the chain registry with a hash or address regex. CSV exports are generated by the API with formula-injection prefixing (`toCsv`). Document downloads are served `attachment` with `nosniff`, `default-src 'none'` and `no-store`. Upload types are allow-listed client- and server-side.

**3. CSP and headers.** `frame-ancestors 'self' https://app.safe.global`, `object-src 'none'`, `base-uri 'self'`, `form-action 'self'`, `upgrade-insecure-requests`. `connect-src` covers exactly the wagmi RPC transports and WalletConnect relay and API hosts. `'unsafe-eval'` is added only when `NODE_ENV === "development"`. HSTS, `nosniff`, `Referrer-Policy: strict-origin-when-cross-origin` and a restrictive `Permissions-Policy` (passkeys allowed for self) are set. `sw.js` is served `no-store`. `allowedDevOrigins` is dev-only. The `/api` rewrite target and `NEXT_PUBLIC_*` values are build-time, which the Dockerfile documents.

**4. Service worker and PWA.** It is registered in production only. It never intercepts `/api/*`, non-GET requests or cross-origin requests. Navigations are network-first and never cached; on failure the precached static `/offline` page (no data, no scripts needed) is shown. Client-side RSC fetches are not intercepted, so authenticated payloads are never cached. Only content-hashed `/_next/static/*` files are cache-first. There is no background sync and no queued requests, so nothing that moves funds can be replayed offline. A waiting worker activates only after the user clicks Reload (`SKIP_WAITING`), and old `tokeniq-*` caches are deleted on activate. See FR-30 for versioning.

**5. Auth and session.** Cookies are first-party through the same-origin proxy. Any 401 from a query or mutation redirects to `/login?next=…&reason=session` (now with the safe `next`). 403 and 404 are shown as people-readable callouts, and non-members get 404 from the API. A stale stored org id falls back to the user's first membership. All org data uses `["org", orgId, path]` keys, switching removes them, and sign-out clears the whole cache before a full page load. Better Auth's client is identity-only.

**5a. Idempotency.** Financial creates (payments, obligations, proposals) send an `Idempotency-Key` that is created once per submission and reused on retry; payment and obligation sheets regenerate it when the body changes (`idem.current.body !== body`). The onboarding obligation rows use the row's UUID, which is safe because the API releases a key on any non-2xx response, so a failed row can be edited and retried. If a success response is lost and the row is then edited, the API's `422 idempotency_key_reused` correctly prevents a second obligation and its message is shown. `POST /sample-workspace` returning 200 (`created: false`) or 201 is handled as success by both callers.

**6. Money display.** USD and token amounts stay decimal strings or bigint end-to-end. `parseFloat` and `Number` appear only in chart geometry, layout percentages, bps conversions of already-exact strings, counts and dates. Sums use `parseDecimal` and `wadToString`. Display rounds half away from zero to the precision shown (`formatDecimal`), and every figure's exact value is one hover or screen-reader read away: compact figures keep it in the title and, now, in the accessible text. Engine-side requirement and availability rounding (up and down respectively, ADR 0003) happens before display. Missing or stale prices are flagged ("No price: excluded from totals", "Stale", the treasury data-issue list, the freshness indicator turning amber), never hidden. The proposal page now shows the token amount exactly (all decimals) next to raw base units when the action names its token (payments). Allocations and withdrawals carry no symbol in the action, so the Details row shows base units, and the decoded calls show the exact token amount once the transaction is prepared.

**7. Accessibility.** Dialogs, sheets, menus, tabs, selects and the radio "segmented" control are Radix primitives with focus trap and return, Escape and roving focus. The command palette is a combobox with `aria-activedescendant`. A skip link, a global `:focus-visible` ring and a single `h1` per page are in place. `Field` wires labels, hints and errors (`role="alert"`). Status is always icon + text (`StatusBadge`, `Callout`). Reduced motion zeroes CSS transitions and animations, and the recommendations scroll honours it. Skeleton loading states use `role="status"` with text. Charts have text summaries and a table alternative.

**8. Error, empty and partial states.** If the API is unreachable, the shell shows "Can't reach TokenIQ right now… Nothing was changed" with a retry and a status link. Pages show empty states that explain what will appear. Stale or partial data is surfaced by `Freshness` and the treasury issue list. The sample-workspace banner sits in the sticky app header on every `/app` page and is repeated on recommendations, proposals and the printable snapshot.

**9. Supply chain from the frontend.** There are no third-party scripts or analytics, and fonts are self-hosted through `next/font`. Wallet code (wagmi, viem connectors, WalletConnect) is dynamically imported with `ssr: false`, only on the signing, verification and wallet sign-in screens; marketing pages never load it. WalletConnect is configured only when a project id is set. The `NEXT_PUBLIC_*` variables are the site URL, the WalletConnect project id (public by design), contact and security emails, the source URL and the service-worker switch, so no secrets.

## Limitations

- **No real wallet or hardware wallet was used, and nothing was signed.** The verifier and review panel were tested with unit tests built from real encodings (viem) and checked for runtime errors on a live proposal page. A prepared transaction could not be rendered end to end, because the sample workspace cannot prepare one (by design) and no real Safe was available. Someone should prepare a proposal on a testnet Safe (Base Sepolia) and compare the panel's three hashes with a Ledger or Trezor's blind-signing screen before relying on it.
- WalletConnect was not configured, so the QR modal and its CSP needs (FR-29) are unverified.
- Accessibility was checked with axe (the e2e suite), code reading and the accessibility tree. No manual screen-reader pass (VoiceOver or NVDA) was done.
- The built-in browser pane was hidden during the session, so it rendered no frames (no `requestAnimationFrame` or ResizeObserver callbacks). Visual and reflow checks depended on DOM measurement and the e2e suite.
- The Approve/Reject confirmation (FR-38), the delete-sample dialog (FR-45) and the invite sheet's email-failed state (FR-44) were type-checked and the pages carrying them were rendered and axe-scanned, but the dialogs were not opened in a browser. The sample proposal is self-proposed, so it offers no Approve button, and the harness mailer always succeeds.
- The API was being changed by another reviewer at the same time. API behaviour described here (FR-05, FR-14) was read from the tree on 2026-10-11 and should be re-checked against the final API.
- This is an internal self-review, not an audit. It found and fixed issues in the code it read, and it says nothing about code it did not read.
